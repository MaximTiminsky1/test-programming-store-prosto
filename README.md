# Посты — Next.js App Router + TypeScript

Список постов из [JSONPlaceholder](https://jsonplaceholder.typicode.com), страница отдельного
поста и форма создания через Server Action с валидацией Zod.

**Стек:** Next.js 16 (App Router), React 19, TypeScript strict, Tailwind CSS 4, Zod 4,
Vitest (unit), Playwright (E2E).

**Демо:** <!-- TODO: прод-URL -->

## Запуск

```bash
npm install
npm run dev      # http://localhost:3000
```

## Проверки

```bash
npm run lint       # eslint (flat config)
npm run typecheck  # next typegen && tsc --noEmit
npm test           # vitest run
npm run build      # продакшн-сборка
npm run check      # всё перечисленное одной командой

npx playwright install chromium   # один раз
npm run test:e2e                  # собирает приложение и прогоняет сценарии
```

Playwright сам поднимает локальный fixture-API (`tests/fixture-server.mjs`) и собранное
приложение на отдельных портах, поэтому E2E детерминированы и не зависят от доступности
внешнего сервиса. Источник данных переключается переменной `API_BASE_URL` (см. `.env.example`) —
через неё же тесты подставляют fixture. API должен поддерживать `GET /posts`, `GET /posts/:id`
и `POST /posts` в формате JSONPlaceholder.

## Структура

```
src/
  app/
    layout.tsx                 каркас: шапка, контейнер, подвал
    (list)/page.tsx            список постов (Server Component) + поиск
    (list)/loading.tsx         скелетон только для списка
    error.tsx                  ошибка загрузки данных (Client Component)
    not-found.tsx              404
    posts/[id]/page.tsx        страница поста + generateMetadata
    posts/new/page.tsx         страница формы
    posts/new/actions.ts       Server Action создания поста
  components/                  PostCard, SearchForm (server), NewPostForm (client)
  lib/                         api.ts, validation.ts, types.ts, post-form-state.ts
tests/
  fixture-server.mjs           детерминированный локальный API для E2E
  e2e/posts.spec.ts            сценарии Playwright
.github/workflows/
  ci.yml                       проверки на каждый PR + деплой в dev после main
  deploy-production.yml        ручной деплой в prod с апрувом
vercel.json                    отключает гит-интеграцию Vercel в пользу Actions
```

Тесты лежат рядом с кодом: `*.test.ts` для `api.ts`, `validation.ts` и Server Action.

## Принятые решения

**Список — Server Component.** Данные тянутся прямо в `page.tsx` через `fetch` с
`next: { revalidate: 60, tags: ["posts"] }`. Клиентские компоненты только там, где без них
нельзя: форма (нужны `useActionState` и pending-состояние) и `error.tsx` (обработчик ошибок
React обязан быть клиентским).

**Zod на двух недоверенных границах.** TypeScript ничего не гарантирует в рантайме, поэтому
схемами проверяются и `FormData` в Server Action, и JSON от внешнего API. Тип `Post` выведен из
схемы через `z.infer`, так что тип и рантайм-проверка не разойдутся. Любой сбой API — статус,
сеть, невалидный JSON, неожиданная структура — приводится к одному `PostsApiError`.

**Поиск в URL, обычной GET-формой.** `/?q=...` переживает перезагрузку и кнопку «назад», ссылку
можно скопировать, страница остаётся серверной и работает без JavaScript. Фильтрация идёт по уже
полученным 100 демо-записям; для реального каталога её нужно перенести в API, оставив в URL те же
параметры.

**Группа маршрутов `(list)`.** `loading.tsx` в корне `app/` создал бы Suspense-границу для всех
страниц, и скелетон списка мелькал бы на странице поста. Группа не меняет URL, но ограничивает
скелетон списком.

**Форма.** Server Action возвращает состояние (`status`, `message`, `fieldErrors`, `values`),
компонент читает его через `useActionState`. Введённые значения возвращаются обратно, чтобы текст
не терялся при ошибке; на успехе форма очищается `formRef.reset()`, так как поля
неконтролируемые. `useFormStatus` вынесен в компонент кнопки: хук читает ближайшую родительскую
форму и в компоненте, который сам рендерит `<form>`, всегда возвращал бы `pending: false`.

**`post-form-state.ts` отдельным файлом.** Файл с `"use server"` может экспортировать только
async-функции, поэтому начальное состояние живёт вне `actions.ts`.

**`typecheck` вызывает `next typegen`.** Типы маршрутов (`PageProps`, `LayoutProps`) Next
генерирует во время сборки, поэтому на свежем клоне `tsc --noEmit` сам по себе падает с
`Cannot find name 'PageProps'`.

**`error.tsx` не печатает `error.message`.** В продакшне Next заменяет сообщения серверных ошибок
на общее и отдаёт только `digest`, поэтому пользователю показывается стабильный текст, а `digest`
выводится отдельной строкой для сопоставления с логами.

**Ограничение JSONPlaceholder.** POST не сохраняет данные и всегда возвращает `id: 101`, поэтому
созданный пост в списке не появляется; в интерфейсе это подписано. `revalidatePath("/")` в экшене
оставлен — с реальным API нужен именно он.

## CI/CD

Два workflow и два окружения.

| Событие | Что происходит |
| --- | --- |
| Любой pull request | Полный прогон проверок. Деплоя нет |
| Push в `main` | Те же проверки, и только после их успеха — автоматический деплой в **dev** |
| Ручной запуск `Deploy production` | Быстрая перепроверка коммита и деплой в **prod**. Требует апрува в GitHub Environments |

**`ci.yml`** — качество и dev-деплой:

```
npm ci → lint → typecheck → unit-тесты → playwright install → build + E2E
                                                                  ↓
                                       (только push в main) deploy → dev
```

Порядок шагов — от дешёвого к дорогому: ошибка линта или типов останавливает прогон за секунды,
а не после полной сборки. Приложение собирается ровно один раз: сборку делает `test:e2e`
(`next build && playwright test`), Playwright поднимает уже собранный билд. Джоба `deploy-dev`
объявлена через `needs: quality`, поэтому в dev физически не может попасть код с красными
тестами. `concurrency` отменяет прогон, если в ту же ветку прилетел новый пуш.

**`deploy-production.yml`** — только ручной запуск (`workflow_dispatch`). Джоба объявляет
`environment: production`, у которого в настройках репозитория включены required reviewers, так
что запуск встаёт на паузу и ждёт подтверждения человеком. Отдельный шаг отказывается
деплоить что-либо, кроме `main`. `concurrency: production` без отмены гарантирует, что два
продакшн-деплоя не пойдут внахлёст.

Деплой выполняется через Vercel CLI, а не через гит-интеграцию Vercel: `vercel build` собирает
артефакт прямо в раннере, `vercel deploy --prebuilt` его публикует. Так деплоится ровно тот
коммит, который только что прошёл проверки, а не отдельная сборка, запущенная параллельно.
Поэтому же в `vercel.json` стоит `git.deploymentEnabled: false` — иначе на каждый пуш
происходило бы два деплоя, из Actions и из интеграции.

Секреты репозитория: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`.

Dev-деплой попадает в preview-окружение Vercel, прод — в production; переменные окружения
задаются в проекте Vercel отдельно для каждого и подставляются на этапе `vercel pull`.

## Использование AI

Основная реализация написана с помощью AI-ассистента (Claude Code): разметка и Tailwind-классы,
черновики модулей, первые версии тестов и workflow. Архитектурные решения из раздела выше —
границы Server/Client, поиск в URL, Zod на границах API, группа `(list)` — задавались мной, и я
разбирал каждый файл перед тем, как оставить его в проекте.

Что проверялось и что это дало:

| Проверка | Результат |
| --- | --- |
| Запуск приложения, а не только `npm run build` | Нашлась ошибка: `initialCreatePostState` экспортировался из файла с `"use server"`. Сборка была зелёной, но страница падала в рантайме (`A "use server" file can only export async functions, found object`). Состояние вынесено в `src/lib/post-form-state.ts` |
| Прогон из чистой установки (`npm ci` в пустой директории) | Нашлась ошибка порядка: `typecheck` падал раньше `build`, потому что типы маршрутов генерирует сборка. Починено внутри скрипта (`next typegen`), а не перестановкой шагов в CI |
| Ревью сгенерированного `api.ts` | В черновике ответ API приводился к типу через `as Post[]` — типы врали бы при любом изменении контракта. Заменено на `postsSchema.safeParse`; `response.json()` тоже завёрнут, иначе невалидный JSON выходил бы наружу как `SyntaxError` |
| Ревью обработки ошибок Zod | Черновик использовал `error.flatten()` — в Zod 4 он устарел, а типизация полей была `string[]` вместо одного сообщения. Заменено явным проходом по `error.issues` |
| Ревью CI-workflow | В черновике были две независимые джобы: приложение собиралось дважды, и падение E2E не отменяло лишнюю сборку. Сведено в один пайплайн с одной сборкой |
| Проверка, что тесты не пустые | Границы в схеме менялись вручную — соответствующие тесты краснеют |
| Сценарии в браузере | Список, поиск, пустая выдача, страница поста, 404, валидация формы, повторная и успешная отправка, мобильная вёрстка. То же зафиксировано в E2E |

Перед сдачей прогнаны `npm run check` и `npm run test:e2e` — без ошибок и предупреждений.

## Что стоило бы сделать для production

Осознанно вне объёма тестового, потому что требует бэкенда:

- реальное хранилище вместо демо-API и, как следствие, работающая ревалидация списка;
- отдельный экземпляр API для dev и prod: сейчас оба окружения ходят в один публичный
  JSONPlaceholder, и разделение окружений существует только на уровне доставки;
- аутентификация и серверная авторизация операций;
- поиск и пагинация на стороне источника данных;
- rate limiting на создание постов (защита от двойной отправки уже есть — кнопка блокируется
  через `useFormStatus`);
- структурированные логи и метрики ошибок внешних запросов вместо `console.error`.
